# Rethinking `service` chart scope: shared resources vs. shared fragments

See `docs/adr/0006-hand-rolled-service-chart-over-bjws-common.md` and `.scratch/shared-service-chart/spec.md` for the original decision record that created `kubernetes-v2/charts/service`.

## Problem Statement

`kubernetes-v2/charts/service` was built to replace copy-pasted Deployment/Service/PVC/IngressRoute boilerplate across ~32 charts with one shared, standalone Helm chart that apps opt into via `chart: service` in their `deploy.yaml`. The first two migrations (`habit-tracker`, `seerr`) were clean fits with zero chart changes needed.

Since then, every further migration attempt has needed the shared chart's schema extended, and the extensions are getting progressively less reusable:

- **`discord-bot`**: needed `ExternalSecret` rendering added to `service` (it only referenced an externally-created Secret before). This generalized well — a follow-up survey found all 14 existing `ExternalSecret`-using charts in the repo share the exact same shape (one remote Vault key, 15s refresh, `vault-homelab` `ClusterSecretStore`, N properties). Low-risk addition.
- **`cloudflare-ddns`**: needed plain literal `env[]` vars added (generalizes — many charts use plain env vars) *and* a container-level `securityContext` passthrough. A survey of every other chart's `deployment.yaml` found `securityContext` hardening is a **one-off** — `cloudflare-ddns` is the only chart in the repo that uses it. We added shared-chart surface area for a single consumer.
- **`pihole`**: does not fit at all, even with more extension. It has 4 container ports (DNS UDP/TCP 53, DHCP 67, HTTP 80), **two separate Services** (a LoadBalancer DNS service with a MetalLB address-pool annotation, and a ClusterIP dashboard service), multiple `subPath` volume mounts from one PVC, and a pod-level `hostname` field. This hits two of ADR-0006's own explicitly-named "keep it standalone" triggers ("non-HTTP services", "custom volume mounts beyond the one storage block") at once.

`discord-bot` and `cloudflare-ddns` are already migrated onto `service` (schema extensions included) as of this session. `pihole` was not migrated and was left on its own standalone chart.

**The core issue**: `service` is a *shared, mutable, unversioned* chart (ADR-0006 already names this as a known risk) — every schema addition changes rendered output for every current adopter (`habit-tracker`, `seerr`, `discord-bot`, `cloudflare-ddns`) simultaneously on next ArgoCD sync, with no per-app pin. Three rounds of schema extension across four real migrations means the "small number of common shapes" premise the chart was built on is being falsified faster than expected — this is the same premature-generalization failure mode ADR-0006 already rejected for `bjw-s/common`'s generic schema and for folding `qbittorrent` into a generic multi-container mechanism, just happening incrementally to `service` itself instead of happening all at once.

## Candidate Direction (not decided — needs planning)

Split *what* gets shared from *how* it gets shared:

- **Keep `service`** for the narrow band of apps that are genuinely identical in shape to `habit-tracker`/`seerr` (single container, one HTTP port, one Service, ≤1 storage mount) — this is where it's added real value with zero schema growth. `radarr` looks like another clean fit in this band, not yet attempted.
- **For everything else** (`pihole`, `sonarr`, and arguably `discord-bot`/`cloudflare-ddns` in hindsight), stop routing bespoke shapes through one shared owned-resource schema. Instead, dedupe the specific fragments that are genuinely copy-pasted across many charts — via **symlinked named templates** (a shared `_helpers.tpl` symlinked into each app's own `templates/` directory, so each app keeps its own `deployment.yaml` in full control of its own ports/volumes/containers, but calls e.g. `{{ include "common.ingressroute" ... }}` / `{{ include "common.externalsecret" ... }}` / `{{ include "common.tolerations" ... }}` for the boring, uniform parts).
  - This is ADR-0006's alternative **(c)**, which was already "considered a viable no-one-dependency option" but was dismissed once full-resource sharing via `service` looked sufficient — findings since suggest full-resource sharing isn't sufficient for most of the remaining chart set, so (c) may be worth revisiting for the apps that don't fit `service`'s shape.
  - Fragments known to be genuinely duplicated, from ADR-0006 and this session's surveys: IngressRoute (~637 lines / ~20 charts, per ADR-0006), `ExternalSecret` (uniform shape across 14 charts, confirmed this session), the standard `node.kubernetes.io/unreachable` toleration block, the NFS PV+PVC pair pattern.

## Open Questions for Planning

1. Should `discord-bot` and `cloudflare-ddns` be migrated *off* `service` and onto standalone charts using shared fragments instead — reverting the `ExternalSecret`/`env`/`securityContext` schema growth on `service` — or is it acceptable to leave them as-is since they already work and `securityContext` is opt-in/harmless to non-users?
2. What's the actual mechanism for symlinked `_helpers.tpl` in this repo's layout — one file at `kubernetes-v2/charts/_common/_helpers.tpl` symlinked into each consuming chart's `templates/`? Does `helm template`/ArgoCD's chart resolution handle symlinks correctly in this repo's CI/deploy path? (Needs a spike, not an assumption.)
3. Which fragments are worth extracting first — is IngressRoute (highest line-count payoff per ADR-0006) the right place to start, ahead of ExternalSecret?
4. Does `service` keep its current `ExternalSecret`/`env`/`securityContext` fields regardless (for its narrow existing/future clean-fit adopters), or do those move to fragments too, with `service` itself calling the shared fragment internally rather than owning the field?
5. What's the actual criterion for "clean fit for `service`" going forward, precise enough to apply to `radarr`, `sonarr`, and the rest of the ~32 charts without another round of case-by-case discovery? (Candidates from this session: single container, one Service/one port, HTTP-shaped, ≤1 storage mount, no pod-level fields like `hostname`.)
6. Does this warrant an ADR update/supersession of ADR-0006, or a fresh ADR once the direction is settled?

## Further Notes

- Full chart-by-chart fit survey done so far (this session): `recyclarr` doesn't fit (`CronJob`, not `Deployment`); `relay` bundles two apps (ingest + notifier), bespoke like `qbittorrent`; `nats` uses `IngressRouteTCP` not HTTP `IngressRoute`; `sonarr` additionally has `ServiceMonitor`/`PrometheusRule` CRs that `service` doesn't render (same category of gap as `ExternalSecret` was, unresolved). `jellyfin` doesn't fit (wraps the official upstream Jellyfin chart, opaque to `service`'s schema); `homeassistant`/`matter-server` don't fit (conditional `hostNetwork`/`dnsPolicy` pod-level fields, dual Services). `radarr` (`deployment` + `ingressroute` + `service` + `pvc`, no secrets, no probes) remains the one clean-fit candidate not yet attempted — but per the decision below, `service` is frozen and no further migrations are being pursued, so `radarr` stays on its own chart for now too.

## Decisions

Reached via a grilling session on 2026-08-22. Supersedes/resolves the "Open Questions for Planning" above.

1. **`service` is frozen at its current 4 adopters** (`habit-tracker`, `seerr`, `discord-bot`, `cloudflare-ddns`). No further hunting for clean fits (`radarr` not pursued under it). Formal "clean fit" criterion, kept for the record even though not being actively applied: single container, one Service/port, HTTP-shaped, ≤1 storage mount (no `subPath`), exactly one `Deployment`, no extra CRs (`ServiceMonitor`/`PrometheusRule`/`CronJob`/etc), no pod-level fields (`hostname`, `hostNetwork`, ...).
2. **`discord-bot`/`cloudflare-ddns` stay on `service` as-is.** Not reverted — the schema growth they caused (`ExternalSecret`, `env[]`, `securityContext`) is accepted as sunk cost, not undone.
3. **New sharing mechanism for the rest of the chart set: `kubernetes-v2/charts/_common`, a Helm library chart** (`type: library`). Consuming charts declare it as a local relative dependency in their own `Chart.yaml` (`repository: "file://../_common"`, exact pinned `version`) and `include` its named templates (e.g. `common.ingressRoute`, `common.externalSecret`) into their own hand-written `templates/`. Each app keeps full control of its own `deployment.yaml`/pod shape — only the genuinely uniform fragments (IngressRoute ~20 charts, ExternalSecret ~14 charts, the unreachable-node toleration block, the NFS PV+PVC pair) are shared.
   - Rejected: symlinked `_helpers.tpl` (technically viable, confirmed via spike — ArgoCD's git checkout preserves symlinks and Helm's loader resolves them — but rejected on taste grounds as "hacky").
   - Rejected: a generic composable values-schema chart (`services: []`/`volumes: []`-style, `bjw-s/common`-shaped). Would revive the exact premature-generalization failure mode ADR-0006 already rejected.
4. **No vendoring required.** ADR-0006 rejected a local library chart (its option (b)) specifically because of the `Chart.lock`/vendored-`.tgz`/`helm dependency update` workflow overhead. That premise no longer holds: confirmed via ArgoCD's own source (`reposerver/repository/repository.go`) that its repo-server does a **full git clone** (not a sparse checkout of just the app's `source.path`) and **automatically runs `helm dependency build`** before templating on every sync (gated by a one-per-checkout marker file, not a toggle). A `file://../_common` relative dependency therefore resolves live against `_common`'s current source on every sync — no `charts/*.tgz` or `Chart.lock` needs to be committed. This is confirmed at the source-code level only, not in official ArgoCD docs, so it needs a smoke test before being relied on further (see below).
5. **Versioning: exact pin per consuming chart**, not a range. A global rollout to all consumers is a deliberate, visible multi-chart edit (bump the pin + let auto-build resolve it), not an automated/tooled action — no bulk-bump tooling is being built now (premature, no real usage yet).
6. **Migration of existing IngressRoute/ExternalSecret users is opportunistic only** — a chart adopts `_common` when it's otherwise being touched, no dedicated migration sweep across the ~20/~14 current users.
7. **`service` itself will eventually consume `_common`'s fragments internally** (rather than owning inline duplicate copies of IngressRoute/ExternalSecret rendering), once those fragments exist and are proven out. Timing not yet scheduled.
8. **First fragment to build, as a smoke test: IngressRoute**, wired into `seerr`. (Note: during planning, ExternalSecret was recommended first as the lower-variance option; the user chose IngressRoute instead since it's easier to visually verify end-to-end.) The smoke test's purpose is narrowly to prove the `file://` local-dependency + auto-`helm dependency build` mechanism (point 4) actually works via a real ArgoCD sync — not yet a broader migration.
9. **ADR-0006 needed a follow-up ADR**, since this reverses its rejection of a local library chart (option (b)) on the strength of new information about ArgoCD's dependency-resolution behavior, while leaving ADR-0006's other conclusions (reject `bjw-s/common`, reject a generic `containers: []` schema, keep `service` standalone rather than a dependency) intact. See `docs/adr/0007-common-library-chart-for-shared-fragments.md`.

## Next Step

Smoke test done locally (`helm dependency build` + `helm template`, matching what ArgoCD's repo-server runs). Real ArgoCD sync still needs to be observed to fully confirm the `file://` + auto-`helm dependency build` mechanism (point 4 of Decisions) — this was only verified locally, not yet via an actual cluster sync.

Two things changed from the plan during implementation, both load-bearing:

1. **The library chart could not be named `_common`.** Helm's chart loader silently skips any file/directory whose basename starts with `_` (the same rule that keeps `_helpers.tpl` from being rendered as a manifest) — applied to a *subchart directory name* under `charts/`, this makes a dependency named `_common` invisible to Helm's own dependency resolution: `helm dependency build` fetches it into `charts/_common-0.1.0.tgz` successfully, but `helm template`/`helm lint` then immediately fail with `found in Chart.yaml, but missing in charts/ directory: _common`, because the loader can't see the extracted `_common` dir either. Confirmed via a minimal repro before and after renaming. The chart is now `kubernetes-v2/charts/common` (named template still namespaced `common.*`, e.g. `common.ingressRoute`).
2. **`seerr` was not "wired in" as a `service`-chart consumer** — it has no `Chart.yaml`/`templates/` of its own (`values/prod/seerr/deploy.yaml` was `chart: service`), so there was nothing under the name "seerr" for `_common`/`common` to be wired into. Per user decision, `seerr` was reverted to its pre-ADR-0006-migration standalone chart (restored from git history at commit `648883b^`) and *that* standalone chart now depends on `common` for its IngressRoute. `seerr` is consequently no longer one of `service`'s 4 adopters — `service` is now down to 3 (`habit-tracker`, `discord-bot`, `cloudflare-ddns`). This should be reflected in decision 1 above and in ADR-0007's "frozen at its current 4 adopters" line if this ADR/spec is revisited.

No vendored artifacts (`Chart.lock`, `charts/*.tgz`) were committed — they were generated locally to verify the mechanism, then deleted.
